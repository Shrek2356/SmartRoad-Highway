# SiteSafe-Sentinel 项目开发复盘与同类工作方法论

## 1. 项目最终解决的问题

本项目不是单纯的“工地图像分类器”，而是一套将开放视觉异常转换为可处置安全事件的系统：

```text
工地摄像头 / 无人机 / 安全员手机
        ↓
YOLO实时注意初筛 或 周期性全图审计
        ↓
MLLM开放风险发现
        ↓
RiskSpec结构化编译
        ↓
SAM3定位 + 空间关系/缺失证据核验
        ↓
最终视觉事实 + 置信度 + 不确定性 + 人工复核问题
        ↓
风险推理Agent → 协同处置Agent → 复盘学习Agent
        ↓
PC管理后台 / 门口大屏 / 安全员移动端
```

真正的技术价值不在某一个模型单点能力，而在于把“发现、定位、核验、处置、复盘”用稳定的数据契约连接起来。

## 2. 开发过程的主要演进

### 阶段一：从“MLLM直接看图”建立基线

项目最初验证了云端视觉大模型对工地异常的开放识别能力。这一阶段证明了：

- MLLM能够识别未在YOLO训练类别中的吸烟、倒地、电线危险、机械近距和临边缺少防护等复杂语义。
- 仅用MLLM就可以产生一份看似完整的自然语言报告。
- 但自然语言报告缺少稳定字段、像素位置、反证和不确定性边界，无法直接驱动工单和自动处置。

这个基线非常重要：它让后续每个新模块都必须回答“相比直接MLLM，它究竟增加了什么价值”。

### 阶段二：重新定位CLIP与早期参考框架

开发中曾考察过CLIP Patch Token、Reverse Attention和多尺度语义投影思路。实测后得到的结论是：

- 最终工程的主链不依赖早期参考框架，也不应用它命名最终系统。
- CLIP对全局语义一致性、候选排序和提示辅助有价值，但它不擅长独立理解“人在吊物下方”或“安全带未与锨点连接”这类组合关系。
- 在当前设备上，CLIP额外耗时可能大于它带来的收益，因此最终保留为可选开关，不让它直接决定风险置信度。

可复用经验：不要因为某个模型在论文结构中出现，就强行让它成为产品主链；要通过消融实验确定它是主干、辅助还是应该删除。

### 阶段三：建立RiskSpec与SAM3证据链

为了让MLLM结果可程序化消费，系统建立了结构化中间层：

1. `FirstPassResponse`：场景摘要、风险候选、支持证据、反证、不确定性。
2. `RiskSpec`：风险类型、主体、客体、防护物、区域、SAM3提示词、关系类型和置信度。
3. `evidence.json`：SAM3 Box/Mask/Presence Score、CLIP可选分数和空间关系结果。
4. `visual_verification.json`：最终视觉事实、置信度、可见证据、不确定性和人工复核状态。
5. `DetectionEvent`：对前端、工单和Agent屏蔽模型实现差异的标准事件。

SAM3的职责被限定为“找到与语义提示对应的像素区域”，而不是独立判定安全风险。例如，SAM3可以定位人员、安全带、吊物和临边区域，但“是否违规”仍需MLLM语义与程序关系核验。

### 阶段四：从穷举风险转向开放发现

早期策略会把风险目录中的所有类型逐项询问MLLM。优点是覆盖稳定，缺点是：

- 类别越多，提示越长，推理越慢。
- 过度穷举容易让模型“为每个类别找证据”，增加幻觉和误报。
- 目录之外的吸烟、倒地和新型现场风险仍可能被忽略。

后续改为“开放发现 + 少量高优先级安全先验 + 支持证据/反证”。上游实时模型若已给出大概异常区域，将其作为注意力提示，但明确告知MLLM：输入大概率为异常，仍必须寻找支持证据和反证，并保留目录外风险发现。

### 阶段五：本地Qwen与“零API成本”实验

系统将报告生成和风险发现从云端模型切换到本地Qwen视觉模型，完成了纯本地调用链路。比较结果表明：

- 云端更强模型通常在小目标、复杂空间关系和稳定JSON输出上更好。
- 本地8B量化模型在正确提示、分块ROI、异常先验和结构化修复下，能够完成主链，但对远景人员、安全带挂点和模糊临边更敏感。
- 输出缺少 `confidence` 被程序默认为0，曾造成“模型已识别但程序过滤”的伪漏检。这说明解析器和缺省值策略也是模型效果的一部分。

可复用经验：更换MLLM时不应只比较“最终命中率”，还要分别检查视觉发现、JSON遵循、字段完整、关系理解和推理耗时。

### 阶段六：V1–V4迭代与“过度审核”教训

为了抑制误报，中期曾逐步增加独立审核、多轮复核、更强空间门控和更多裁剪调用。这出现了典型的负优化：

- 模型发现的真风险在后续严格审核中被撤销，召回下降。
- 对正常对照样本的多轮搜索反而提高了“总要找出什么”的偏置，误报上升。
- 每张图调用次数增加，延迟显著上升。
- 当关系审核本身不稳定时，它不是“保险”，而是新的错误源。

最终策略回到较轻的V1主干，只针对明确问题增加低成本修复：机械近距关系、安全帽头部ROI、安全带腰背/挂点ROI、临边区域分块、缺失置信度回填和安全绳“已连接可靠锨点”提示。

这是项目最重要的工程教训之一：**每增加一个审核步骤，必须同时证明它降低了误报、没有不可接受地伤害召回，且耗时增量值得。**

### 阶段七：引入YOLO实时调度，但不让其封死开放风险

实时摄像头不可能对每帧运行重型MLLM。系统因此使用两套YOLO输出`ScreeningTrigger`：

- 已训练违规类别可直接触发VLM。
- 人员、机械、车辆等中性目标提供注意区域，不直接等于异常。
- 纯代码可根据人员—机械粗框距离生成关系候选。
- YOLO失败采用故障开放，不让轻模型故障成为漏检单点。
- 每30分钟或2小时强制全图审计，人工上传也可直接绕过YOLO，从而发现倒地、吸烟、电线和临边等YOLO训练集中没有的类别。

关键原则：**YOLO是调度器和视觉注意力初筛器，不是开放异常的最终法官。**

### 阶段八：从算法脚本变成完整产品链

后期工作不再只关注“一张图能否识别”，而是完成：

- `detect_bridge.py`（8810）：上传、摄像头帧、定时全审计、任务进度、模型路径、Qwen启停和知识库导入。
- `app_server.py`（8800）：鉴权、风险事件、工单、通知、案例、复盘和前端聚合数据。
- PC管理后台、大屏、移动端三端界面。
- 模型配置页：可选路径、本地/云端档位、API Key、CLIP开关、Qwen启停和知识库导入。
- 明暗主题、权限守卫、登录动画、案例展示、检测结果和Agent闭环页面。
- Demo、本地离线、云端API三档启动及便携部署。

工程难点从模型调优转向了“Mock与真实数据如何共存、服务如何启停、路径如何可配置、展示素材如何不被误当成真实数据”。

### 阶段九：交付、授权和可复现性

最终交付分为完整验收版和轻量比赛补充资料版。交付工作包括：

- 移除早期框架名、旧版程序、权重、密钥、数据库、详细历史推理文本和调试日志。
- 保留八张关键案例、Overlay、Mask、创意素材、源码、部署指引和必要验证回执。
- 给便携Python、Node/npm、`node_modules`和`dist`设定清晰边界。轻量包最终使用便携Python直接服务已构建的前端，不需`node_modules`也能开箱演示。
- 处理Windows ZIP对中文路径的编码兼容，对压缩包逐文件验证并生成SHA-256。

## 3. 最终技术模块与真正贡献

| 模块 | 真正职责 | 不应越界做的事 |
|---|---|---|
| YOLO实时感知 | 高频抽帧初筛、人/机械/PPE粗框、触发调度 | 不保证发现所有未训练异常，不输出最终风险事实 |
| MLLM | 施工场景理解、开放风险发现、支持/反证、RiskSpec候选 | 不直接把自然语言当数据库事实，不单独证明像素位置 |
| SAM3 | 文本引导的Box、Mask、Presence Score和ROI | 不把“未分割到”等价为“已证明缺失” |
| CLIP | 可选语义一致性、候选排序和提示辅助 | 不做复杂空间关系最终裁决，不是必选路径 |
| 纯代码核验 | JSON修复、缺省值、置信度上限、几何关系、状态机、权限和SLA | 不应用过多硬规则取代视觉事实 |
| 风险推理Agent | 风险等级、规范检索、处置建议 | 不修改锁定的视觉结论 |
| 协同处置Agent | 人工确认、建单、派单、通知、整改证据和关闭 | 不绕过工单状态机直接宣告整改完成 |
| 复盘学习Agent | 案例归档、误报统计、阈值建议、班前交底材料 | 不自动改模型权重或未审批阈值 |

## 4. 最难的技术问题

### 4.1 “缺失”比“存在”难

未戴安全帽、未系安全带、未设临边护栏都属于缺失型风险。分割器找不到防护物时，可能是真缺失，也可能是遮挡、分辨率不足、提示不准或模型失败。最终建立：

- `confirmed_absent`：检查区域充分可见，可确认缺失。
- `not_observed`：未观察到，但证据不足，转人工。
- `occluded`：相关身体、挂点或边缘区域被遮挡。

这比单纯调高置信度阈值更重要。

### 4.2 中远景小目标与注意力丢失

工地全景中人员往往只占很少像素。即使MLLM理解“这是高处作业”，也未必能看清头部、腰背和安全绳挂点。有效方法是：

- 人员预检后对头部、腰背、挂点扩大ROI。
- 全图与局部裁剪同时提供，避免裁剪破坏关系上下文。
- 临边、开口和大型区域使用分块而不是只围绕人员裁剪。
- 对确实无法辨认的样本保留为能力边界，不用规则强制“修满”。

### 4.3 关系型风险不是目标检测

“人员在吊物下方”、“人员离机械过近”、“安全带没有连接锨点”都需要多实体和空间/功能关系。单个Box、Mask或CLIP相似度不能等价于风险。项目通过主体、客体、相对方向、水平重叠、归一化距离和二次语义核验处理，但也必须警惕关系规则过严造成漏检。

### 4.4 数据集标签不等于图像全部真相

公开数据集中出现过：剩余大量图片未按“正常/异常”清晰分类；文件名只表示主标签，图中可能还有其他风险；部分临边、高处或吊装标签需要人工重审。因此评估必须分开：

- 是否发现任意真实异常。
- 是否命中数据集指定主标签。
- 是否完成自动确认。
- 是否正确转入人工复核。
- 是否生成了有效掩码。

不能把“没命中文件名标签”简单等价为“没发现异常”，也不能把数据集未标注风险直接算作误报。

### 4.5 效果、误报和速度的三方权衡

本地MLLM是主要耗时来源，每增加一次全图或ROI复核都可能增加数十秒延迟。项目曾经历“多审核、低召回、高误报、慢速度”同时出现的版本。因此不能只优化单一准确率，而应同时记录：

- 开放发现召回。
- 指定主风险命中率。
- `verified`自动确认召回。
- 包含人工复核的系统找回率。
- 正常对照误报率。
- 有效Mask覆盖率。
- 平均/P95耗时、MLLM调用次数与各阶段耗时。

### 4.6 前端Demo与真实链路容易混淆

为了快速演示，前端需要预置案例、检测框、Mask和看板数据；但为了工程可信，又必须明确区分它们与真实数据库事件。最终解决方式包括：

- 页面展示“演示素材/部分演示数据”标签。
- 演示补位数据使用`presentationAsset`追踪。
- 真实事件通过检测桥和业务后台合并，不伪造数据库记录。
- 生产模式可关闭展示资产。

### 4.7 环境、启动和打包往往比算法更容易阻断交付

开发中遇到的实际问题包括Python版本不一致、FastAPI依赖缺失、检测桥未启动、Qwen服务生命周期、前端`node_modules`和`dist`的取舍、硬编码本机路径、中文ZIP路径兼容以及新电脑首次部署。

经验是：可部署性不能放到最后一天。从第一个可运行版本开始就应建立一键启停、环境自检、相对路径、便携Demo、权重缺失提示和关闭后台流程。

## 5. Agent模块的设计经验

### 5.1 Agent不应与业务模块重复

“异常检测系统”是业务/技术模块；“风险推理、协同处置、复盘学习”才是Agent的决策职责。一个清晰的分工是：

- 视觉模块输出“看到了什么”。
- 风险推理Agent输出“这意味着什么、根据哪条规范、建议怎么做”。
- 协同处置Agent输出“谁在什么时间内处理、如何验收”。
- 复盘学习Agent输出“本次人工结论对未来规则和培训有什么建议”。

### 5.2 学习不等于自动修改模型

演示系统中更可信的“复盘学习”是：记录人工确认/驳回、统计风险类别误报率、生成阈值建议、经人审批后生效，并生成案例库和班前交底。不应宣称系统在没有训练管线和回归验证的情况下会“自主训练变强”。

### 5.3 RAG的最小完整闭环

行业规范导入不是一个文件上传按钮就算完成。完整链应包含：

1. 接收`.md/.txt/.pdf/.docx`。
2. 安全文件名和路径检查。
3. 文本提取、分块和索引更新。
4. 可查询的命中结果、来源文件和相似度。
5. 风险推理结果中附带规范来源。
6. 删除文档后索引同步刷新。

## 6. 评测数据应该怎么看

项目历史上有多种评测集，不能将它们混成一个总正确率：

| 评测范围 | 主要用途 | 正确解读 |
|---|---|---|
| 7/8张关键示例 | 端到端演示、Overlay/Mask和报告检查 | 要区分任务成功、任意风险找回、主标签命中和是否有Mask |
| 58张异常批次 | 迭代期候选发现和门控消融 | 不同版本代码与标签修订过，必须按版本报告，不得把旧结果写成最终结果 |
| 50张正负对照快照 | 误报与保守门控检查 | 某历史快照为0误报/精确率100%，但`verified`召回24%、含人工复核召回44%；这证明其保守，不代表综合效果已达生产水平 |
| 最终提交回归 | 代码、构建、端口和契约健康 | 最终回执为121项后端测试通过，三端构建和5173/8800/8810冒烟测试通过；它证明工程链路，不等于现场精度 |

应当固定每次评测的代码版本、配置、模型、数据集清单、标签修订版、硬件和耗时统计。否则“51/58”、“52张确认”、“43张命主风险”等历史数字很容易被错误对比。

## 7. 下次做类似项目的推荐方法

### 第一步：先定义业务事实，再选模型

先定义风险输出必须包含什么：风险ID、主体、客体、区域、置信度、证据、反证、不确定性、Mask、人工复核和处置建议。再决定哪些由MLLM、分割模型或确定性代码生成。

### 第二步：保留最小基线

建立“一次MLLM直接发现”基线，永久保留运行脚本和结果。后续每加YOLO、CLIP、SAM、复核或规则，都与该基线比较召回、误报和速度。

### 第三步：先冻结数据契约

在模型优化前冻结`ScreeningTrigger → RiskSpec → Evidence → VisualVerification → DetectionEvent`。更换模型时只换适配器，不让整个前后端跟着改。

### 第四步：建立分层评估

对每张图分别标记：

1. MLLM是否提到真风险。
2. RiskSpec是否正确编译。
3. SAM3是否定位正确实体。
4. 空间/缺失门控是否正确。
5. 最终是自动确认、人工复核还是错误撤销。
6. 前端是否正确显示Overlay、Mask、报告和来源。

这比只看一个总准确率更容易定位问题。

### 第五步：用错误类型驱动优化

将失败分为：发现漏检、JSON/字段错误、实体定位失败、关系核验失败、缺失语义错误、标签问题、视觉边界、前端映射错误和环境故障。每次只修一类，然后在异常集和正常对照上同时回归。

### 第六步：设定审核步骤的删除条件

新步骤不仅有“加入条件”，还应预先设定删除条件：如果它对目标错误类别没有显著改善，或让召回/误报/延迟中任一项超过预算，就删除。

### 第七步：将人工复核设计为产品功能

不确定性不是一个需要隐藏的“模型失败”。系统应输出模型已看到的事实、无法确认的部位和要请安全员判断的具体问题，而不是只显示一个“失败”标签。

### 第八步：从第一天就做一键启停和便携Demo

至少应同时保持：

- 不需权重的Demo档，用于前后端、Agent和空数据回归。
- 本地权重档，用于零API成本和私有化。
- 云端API档，用于更强模型与快速验证。

## 8. 可直接复用的检查清单

### 算法与数据

- [ ] 是否有一个最小MLLM基线？
- [ ] 异常样本、正常对照和能力边界是否分开？

- [ ] 缺失型风险是否区分`confirmed_absent/not_observed/occluded`？
- [ ] 数据集标签修订是否有版本和人工依据？

- [ ] YOLO是调度器还是最终决策器，边界是否明确？
- [ ] MLLM输出是否有Schema验证和安全缺省值？
- [ ] SAM未检出是否被错当成缺失？
- [ ] CLIP或其他辅助模块是否有独立消融结果和开关？
- [ ] 每个新复核调用是否同时评估召回、误报和耗时？
- [ ] 是否有周期性全图审计防止YOLO封死未知风险？

### Agent与业务

- [ ] Agent是否只消费锁定视觉事实，而不篡改证据？

- [ ] 人工复核是否有具体疑问、证据和回流位置？
- [ ] 复盘学习是否采用“建议→审批→生效”而不是无监督自改？

### 工程与交付

- [ ] Demo、本地权重、云端API是否分档？
- [ ] 平台启动是否同时管理前端、业务后台、检测桥和模型服务？

## 9. 对当前成果的准确定位

当前项目已经是一套结构完整、接口可替换、可以展示和继续工业化的原型：

- 开放发现、SAM3定位、证据门控、人工复核和Agent处置链已连通。
- 实时YOLO调度与周期全审计同时存在，不会将系统限死在训练类别内。
- Demo、本地和云端档位，三端前端，模型配置和便携交付已完成。

但它仍不应被描述为“已经达到无人值守的生产精度”。投入现场前还需：

1. 用实际摄像头、夜间、雨雾、遮挡和不同工种建立工地级验收集。
2. 重新标定召回、误报、人工复核率和P95耗时。
3. 根据部署GPU选择更强MLLM、量化策略和并发调度。
4. 对YOLO小模型做现场数据增量训练，但仍保留开放全审计。
5. 完成RTSP/流媒体网关、实际通知渠道、权限安全和长期稳定性压测。

因此，最合理的总结是：**我们完成的不是一个把效果全部压在某个MLLM上的Demo，而是一套能够替换更强模型、保留证据边界、支持实时调度与开放审计、并把视觉结果转换为管理闭环的工程框架。**
